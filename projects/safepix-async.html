o problemathe problem

Se a API espera o processamento, uma lentidão ou um reenvio do cliente pode gerar dois Pix. Aqui a API responde logo, o processamento acontece em segundo plano, e o id do Pix é a chave que impede o processamento duplicado.If the API waits for processing, a slow call or a client retry can create two Pix. Here the API answers right away, processing runs in the background, and the Pix id is the key that blocks duplicate processing.

Raio-XX-ray

Fluxo do código: a API só valida, publica e responde 202. A deduplicação e a gravação de estado ficam no consumer, com o PostgreSQL.Code flow: the API only validates, publishes and answers 202. Deduplication and state live in the consumer, backed by PostgreSQL.

O consumer reserva o idThe consumer reserves the id

O tryStart faz um INSERT na tabela pix_processing. Se o id já está PROCESSED, ou tem reserva PROCESSING dentro do timeout (PT5M por padrão), a mensagem é ignorada. Um segundo POST com o mesmo id gera outra mensagem, e é aqui que ela é descartada.tryStart runs an INSERT into pix_processing. If the id is already PROCESSED, or has a PROCESSING reservation inside the timeout (PT5M by default), the message is skipped. A second POST with the same id creates another message, and it is dropped here.

Validação e antifraudeValidation and fraud check

O valor precisa ser maior que zero. O PixAntifraudClient roda dentro do circuit breaker pixAntifraud. Valor inválido ou reprovação viram PixBusinessValidationException, que não passa pelo retry.The amount must be greater than zero. PixAntifraudClient runs inside the pixAntifraud circuit breaker. An invalid amount or a fraud rejection becomes PixBusinessValidationException, which skips the retry.

Sucesso, retry ou DLQSuccess, retry or DLQ

Sucesso: markProcessed grava PROCESSED. Erro transitório: a reserva é liberada e a mensagem tenta de novo, até 3 tentativas, com backoff de 500 ms dobrando até 5 s. Esgotado o retry, a mensagem vai para pix.recebido.v1.dlq.Success: markProcessed writes PROCESSED. Transient error: the reservation is released and the message is tried again, up to 3 attempts, with a 500 ms backoff that doubles up to 5 s. When retries run out, the message goes to pix.recebido.v1.dlq.

Operação: DLQ e métricasOperations: DLQ and metrics

A DLQ funciona como quarentena. POST em /api/v1/admin/dlq/pix/reprocess move mensagens para a exchange pix.recebido.v1.reprocess, que as devolve à fila principal. O Prometheus lê /actuator/prometheus e o Grafana mostra pix.processed.total, pix.failed.total e pix.processing.duration.The DLQ works as quarantine. POST to /api/v1/admin/dlq/pix/reprocess moves messages to the pix.recebido.v1.reprocess exchange, which routes them back to the main queue. Prometheus scrapes /actuator/prometheus, and Grafana shows pix.processed.total, pix.failed.total and pix.processing.duration.

src/main/java/famel/com/safepix_async/controller/PixController.java
    public ResponseEntity<Void> receberPix(
            @RequestHeader(value = CORRELATION_ID_HEADER, required = false) String correlationId,
            @RequestHeader(value = TENANT_ID_HEADER, required = false, defaultValue = DEFAULT_TENANT_ID) String tenantId,
            @Valid @RequestBody PixRequest pixRequest
    ) {
        String resolvedCorrelationId = resolveCorrelationId(correlationId);
        PixEvent pixEvent = pixRequest.toEvent(resolvedCorrelationId, tenantId);

        LOGGER.info("Recebida solicitacao de Pix: id={}, chavePix={}, valor={}",
                pixEvent.id(), SensitiveDataMasker.maskPixKey(pixEvent.chavePix()), pixEvent.valor());
        pixService.enviarPix(pixEvent);
        LOGGER.info("Solicitacao de Pix aceita para processamento: id={}, correlationId={}",
                pixEvent.id(), pixEvent.correlationId());

        return ResponseEntity.accepted()
                .header(CORRELATION_ID_HEADER, pixEvent.correlationId())
                .location(URI.create("/api/v1/pix/%s/status".formatted(pixEvent.id())))
                .build();
    }

A API não consulta o PostgreSQL. Ela valida o corpo (@Valid), publica o evento e responde 202 com Location. O processamento começa depois, no consumer.The API does not query PostgreSQL. It validates the body (@Valid), publishes the event and answers 202 with Location. Processing starts later, in the consumer.

src/main/java/famel/com/safepix_async/consumer/JdbcProcessedPixStore.java
    @Override
    public boolean tryStart(UUID pixId) {
        Instant now = clock.instant();
        int affected = jdbcClient.sql("""
                        INSERT INTO pix_processing (pix_id, status, created_at, updated_at)
                        VALUES (:pixId, :processing, :now, :now)
                        ON CONFLICT (pix_id) DO UPDATE
                            SET updated_at = EXCLUDED.updated_at
                            WHERE pix_processing.status = :processing
                              AND pix_processing.updated_at < :staleBefore
                        """)
                .param("pixId", pixId)
                .param("processing", PROCESSING)
                .param("now", Timestamp.from(now))
                .param("staleBefore", Timestamp.from(now.minus(processingTimeout)))
                .update();
        return affected == 1;
    }

O id do Pix é a chave de idempotência. O INSERT ... ON CONFLICT só devolve true quando não existe linha PROCESSED nem reserva PROCESSING recente. Duas entregas do mesmo id disputam essa linha, e apenas uma segue.The Pix id is the idempotency key. INSERT ... ON CONFLICT returns true only when there is no PROCESSED row and no recent PROCESSING reservation. Two deliveries of the same id compete for that row, and only one continues.

    RetryPolicy pixRetryPolicy(int maxAttempts, long initialIntervalMs, double multiplier, long maxIntervalMs) {
        return RetryPolicy.builder()
                .maxRetries(Math.max(0, maxAttempts - 1))
                .delay(Duration.ofMillis(initialIntervalMs))
                .multiplier(multiplier)
                .maxDelay(Duration.ofMillis(maxIntervalMs))
                .excludes(PixBusinessValidationException.class, AmqpRejectAndDontRequeueException.class)
                .build();
    }

Retry só vale para erro transitório: PixBusinessValidationException está em excludes e segue direto para o recoverer. After the last attempt, RepublishMessageRecoverer sends the message to pix.recebido.v1.dlq.
